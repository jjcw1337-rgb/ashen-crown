## Client error: `Condition "!is_inside_tree()" is true. Returning: Transform3D()` at `get_global_transform (scene/3d/node_3d.cpp:345)` (016d8c012ecbed22): fixed

**Reports.** 1 player (Windows, RTX 5070 Ti, Ryzen 7 9800X3D), 1 session, 16 events, build 4bf5a0c (staging), preset 2
(High), in the camp at (2.2, 3.8), a level-20 Demon. Sent 11-04 00:07:49. The crumbs: start, `enter town` (the camp
behind the title), `enter town` 10 s later (Continue), `enter vigil` (the Last Flame: two `boss` crumbs, the
champions of waves 5 and 10, so the vigil was won), `enter town` (back through the gate), `enter town` 10 s later
(Save and Exit to Title reloads the camp). The same session also sent the two known one-Windows-player engine
issues (28b5fe25d00fd3d0 skeleton_updated, 2bdc80640e965691 tree_exited), so it's the same player as those.
No `at:` script line: an engine error raised from a script call (Godot 4.3 prints no GDScript stack for those).

**Reproduction.** A headless tool script playing the crumbs (a level-20 Demon through the Vigil Gate, a wave fought
with every skill, back to the camp, Save and Exit to Title, the Demon hovered on the Continue dais) showed nothing.
The same script **windowed** (Forward+ on this Mac's Metal/Vulkan) logged it at once, 8 times per camp load, before
the Last Flame was even reached: it's not the Demon or the vigil but **any camp load on Forward+ High or Ultra**
(the player's 16 = 8 + 8 for the two camp loads before the batch went up). `-d` (the local debugger) gives no
stack either; temporary `printerr` lines through `Game.load_zone` put it inside `world.build` (the camp), and the
count (8 = 4 braziers x 2) pointed at the grand waypoint's braziers.

**Cause.** `BrazierCoals._build` (the waypoint's four blue-fire bowls, `scripts/brazier_coals.gd`) runs before the
brazier is added to the tree. With heat haze on (`InfernalFx.haze_ok`: Forward+, High/Ultra, so never headless) it
called `InfernalFx.glow(self, global_position, ...)`: reading its own `global_position` out of the tree is one
error, and `glow` setting the new card's `global_position` (Godot 4.3's `set_global_position` reads
`get_global_transform` first) is the second. Harmless: out of the tree the card ended up at that position as a
local one, and the brazier sets the haze's local position right after. Came in with the coals (35d31fb, 11-01).

**Fix** (`scripts/infernal_fx.gd`, `scripts/brazier_coals.gd`, commit dd606d1). `InfernalFx._place(n, pos)`: a world
position in the tree, the local one while the parent is still outside it (what `particles` already did inline);
`glow`, `flame`, `fire` and `particles` use it. The brazier passes its local origin. Same placement as before.

**Before / after.** Windowed Forward+ boot to the camp (preset 2): 8 errors -> 0. The four braziers still have their
`haze` at local (0, 1.51, 0). Tests: below.

**No cheap regression test:** the path only runs with Forward+ haze on, which headless tests never have; a tool
can't see an engine error from inside the script. Lesson added instead (run the player's renderer).

**Watch.** The issue should stop with the next staging build. If the same message comes back from another place:
any `.global_position` on a node built before it's added (props dressed off the tree) is the same bug.
