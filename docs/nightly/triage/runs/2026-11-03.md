## 1. Client error: `RPC 'sv_zone_ready' on yourself is not allowed by selected mode` (b43c39456b33870a): fixed

**Reports.** 1 player (macOS, Apple M5 Pro), 1 event, build 1a5b251, 11-02 17:03, class Doug, in the camp. The
crumbs: camp, the islands, a death on the Verdant Isle, back to the camp, `raid` (161.35.185.195:24567), `enter bg`,
then `enter town` two seconds later. The raid server took the join and dropped it (the journal shows joins turned away
then: the "Unable to send packet" issue below is the server side of the same moment).

**Cause.** `Net._client_goto` (a client following the host into a zone) awaits `Game.load_zone` and then tells the
host it's ready (`rpc_id(1, "sv_zone_ready")`). The server dropped the client while the crypt was loading:
`_on_server_gone` -> `shutdown()` set the offline peer (whose id is 1) and `Game.on_net_failed` queued the trip home;
then the load finished and the trip sent its RPC to "peer 1" = itself. Harmless (the trip home ran anyway), but an
error in every such case. The raid's hello after the Nakama ticket (`_on_connected`, another await) had the same hole.

**Reproduction.** `tools/net_drop_test.gd` (new): a client link to a port nobody listens on, `_client_goto` to the moor,
`shutdown()` while the zone loads. Before the fix the log shows the exact error; after it, none.

**Fix** (`scripts/net.gd`): `Net.still_joined(link)`: still active, a client, on the same `ENetMultiplayerPeer` as before
the await and connected. `_client_goto` and the raid hello check it after their awaits and stop quietly otherwise.

**Watch.** Nothing expected. The same "await, then RPC" pattern elsewhere would show up as the same message with
another RPC's name.

## 2. Client error: `disconnect a nonexistent connection ... skeleton_updated` (28b5fe25d00fd3d0): watch (2nd night)

**Reports.** Still 1 player (Windows, RTX 5070 Ti, Low), now 150 events over 16 sessions and every build since 11-01
(12 reports in the last 36 h, the newest on a4e2405). New from the crumbs: **every session is just `start`, `enter
town`, `enter town`** (the camp behind the title, then the camp in play; one went on into a raid), 3-26 events a
session (at least 3). Mac players on the same builds, doing the same, report none.

**Investigation.** Read Godot 4.3's `scene/3d/bone_attachment_3d.cpp`: the error can only come from `_check_unbind`
when the attachment is `bound` but the skeleton it finds now (its parent, or the external one) doesn't hold the
connection: a different skeleton than the one it bound to. A scratch scene of bare nodes tried 11 ways
(duplicate in the tree, reparent the skeleton or the attachment, rename the bone, a missing bone, `replace_by`, an
external skeleton freed first, `bone_idx` set outside the tree, `clear_bones`, a duplicated attachment): none
logs it. `class_carousel_test` (every class built and freed on the stage) and the title flow show none on this Mac.
The game's attachments (keepers' held tools `ForestCamp.hold`, the dragons `_attach`, the Wraith's claws, the Sloths)
all set `bone_name` before `add_child` (no binding until in the tree).

**Next.** Harmless so far (an error line). If a second player gets it, or it starts coming with a crash: log the
attachment's path in a crumb when the camp is freed, or try the Windows export template on the camp.

## 5. Slow spot: the archer hitches on the moor and in the fort (reproduced; cause not found yet: watch)

**Reports.** The worst stutter in the data: the archer, Act I moor and fort, preset Low, **both players** (Windows
RTX 5070 Ti 11-02 01:31: 45 hitches in the minute, 1% low 7.7; the Mac, 11-02 01:34-01:44: 9-40 hitches a minute for
12 minutes, 1% low 3-14, p99 up to 298 ms), levels 1-5, 1-11 monsters about. Average fps was fine (35-85). By
comparison Doug on the same Mac (11-02 15:22): 20 then 15 hitches in his first two minutes on the moor, then nothing,
which looks like first-use shader/pipeline compiles; the archer's go on all session.

**Reproduction.** `--kpi fight --class archer --quality 0 --secs 30 --trace` (24 monsters, Fire Arrow every 1.2 s):
fps 87, 1% low 28.6, **6 hitches/min** (frames of 125-140 ms); the knight the same way: 96 fps, low 40.9, 0 hitches;
the archer with `--skill none` (the bow alone, 40 s): 99 fps, low 59.9, 0. With temporary prints at every ArrowFx
step and spawn, **every hitch is the frame right after a Fire Arrow `finish`** (the burst where it ends: its light,
the fireball sim cards, the smoke column, the Decal scorch). Only ~1 finish in 12 hitches, and the hitched ones
run the same steps as the others.

**Bisect (not conclusive).** Normal runs: 3 of 5 had a hitch (6, 4, 0, 2, 0 a minute). Scorch Decal off: 0 of 2.
The scorch's emission map always set (zero energy where it shouldn't glow, so the decal atlas never loses it): 0 of 2.
A theory that fits "now and then": the decal atlas is rebuilt whenever a texture's users go 0 -> 1 (the scorch's
emission map is only used on glowing ground, not stone). But a scratch scene doing exactly that with these textures
costs nothing measurable, and in two more normal runs where every arrow landed on grass nothing hitched either.
Without a clear cause, nothing was changed.

**The lead: first-use shader compiles.** A scratch scene (Forward+, this Mac, cold cache): the first GPUParticles3D of
each `ParticleProcessMaterial` variant (plain / rigid collision + bounce / turbulence) costs **450-770 ms** in its
frame; re-creating the same variant later, even after the last one was freed, costs nothing. Fire Arrow's burst
builds different variants by the ground it lands on (`ArrowFx.surface`: grass settles, stone bounces and chips, dirt
dusts, wood keeps burning, `"surfaces"` in the preset), so a new combination compiles once in the middle of a fight,
and a moor full of new monsters and effects keeps meeting new ones (Doug's first two minutes too). In the KPI the
shader cache is warm after a few runs, which is why runs hitch less and less: logging each finish's surface, one hitch
came 10 frames after the first stone landing, but another had nothing new and other first stone landings didn't hitch
(the gate was running beside these runs).

**Next.** The likely fix is a warm-up behind the loading screen: draw each of the class's effects once (every
ArrowFx preset's release / pierce / burn / finish on every surface, off camera for a frame) when a zone loads, so the
compiles happen there. Measure it with a cleared `user://shader_cache` and pipeline cache (the players' state after a
new driver or first install). Also: run 10+ of each variant (`ab_*` in the night's folder) to settle the scorch; check the light's shadow
(`Fx.effect_shadow` turns it on 0.04 s later, and the dual-paraboloid maps are new as of 2026-11-03's perf night) and
the fireball's cards one at a time; on a GPU capture (Xcode's Metal capture of the KPI run) the 130 ms frame
would show whether it's a pipeline compile or the GPU waiting. Watch the archer's samples on the newest builds.
